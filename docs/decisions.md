# Checks Toolkit — Decisions Log

Every decision here is checked against the core principle in
[architecture.md](./architecture.md): if a consumer repo would need to
know *how* CI works, that knowledge belongs in `checks-toolkit`, not in
the consumer.

This is the source of truth for **why** things are the way they are. The
actionable checklist lives in
[roadmap.md](./roadmap.md).

| Topic | Decision | Reason |
|---|---|---|
| Repo name | `checks-toolkit` | Broader than just CI; room for CD, security, runners, tooling |
| Description | "A centralized DevOps platform providing reusable CI/CD workflows, security automation, and deployment tooling" | Covers the scope without locking into GitHub Actions only |
| Git hosting | GitHub | Mergify integration and workflow keep working |
| Change detection | **Fully automatic** (no per-project config by default) | Minimal configuration per consumer repo; a project-level override file remains an escape hatch, never a requirement |
| Security model | 3 layers: always-on / conditional / scheduled | Prevents every PR from running all scans, while secret scanning stays active even on `.md`-only changes |
| MVP scope | Detection+CI for Python, Node, Docker, Terraform, Markdown; Security: Gitleaks, CodeQL, Trivy | Small enough to prove the concept before scaling up |
| Runner separation | Separate `ci` and `deploy` runner labels (concept now, machine later) | CI runs potentially untrusted PR code; must never see production credentials |
| Versioning | Exact Git tags (`v0.1.0`, ...) that are never moved. Consumers pin to the exact tag and repeat it in `platform-ref` | A moving ref (`@development`, or a floating `@v1`) lets a change reach every consumer without them choosing it; exact tags make every upgrade deliberate |
| First tag is `v0.1.0`, not `v1.0.0` | The platform is pre-1.0, so a `0.y.z` tag (SemVer's "anything may change" range) is the honest signal. `checks-toolkit-test` pins to the exact tag, not to a moving alias | `v1.0.0` should mean "stable enough to make a breaking-change promise around", which is not true yet. Revisit once enough real tooling exists to warrant that promise |
| Default branch | `development` stays the default/main line of `checks-toolkit` (not switching to `main`) | |
| Account/org | GitHub Organization: **`ops-lane`** — platform only (checks-toolkit + test-consumer repos) | Name reflects the core principle: every change flows through a fixed "lane" (detect → CI → security → merge) |
| Logo/branding | Final concept: navy (#1B1F3B) + cyan (#00E5FF) accent, "lanes converging into one direction" motif. **Lives at the `ops-lane` org level, not inside this repo** | The logo represents the Ops Lane organization, not just `checks-toolkit`; keeping it here would misscope it. Asset location at the org level is still to be decided (e.g. an `ops-lane/.github` profile repo) |
| `detect-changes` implementation | MVP: existing action or a custom script; **temporary**, with an explicit plan to replace it with an in-house detector | This is the platform's core component — eventually full control over security, versioning, monorepo behavior, and performance is wanted, not a dependency on a third-party action for infrastructure-critical logic |
| Security foundation timing | Minimal security (Gitleaks + minimal permissions) belongs in Phase 1, not Phase 3 | Security isn't a feature you "add later" — the architecture must account for it from the start |
| CodeQL triggering | Decoupled from `changed.*` logic; its own trigger question ("should this analysis start?") separate from the analysis scope | CodeQL analyzes the codebase as a whole, it's not a linter that only needs the changed files |
| Mergify contract | Consumer repos expose exactly two required checks: `CI gate` and `Security gate` — these are GitHub check runs/statuses, not workflow outputs | Mergify looks at checks/statuses, not `workflow.outputs`; the internal job structure can change freely without ever touching the Mergify config |
| `skip-ci` PR label | Adopted as an official part of the technical contract (see [workflows.md](./workflows.md#skip-ci-label)) | Lets a maintainer deliberately override CI (including security) via a label, without leaving required checks stuck "pending" |
| License | MIT, `LICENSE` file at the repository root | Originally no license while the repository was private. Without a license file nobody may legally use the code, so it is added before the repository goes public. MIT is short, permissive and common for reusable CI tooling |
| First consumer repo | Separate `ops-lane/checks-toolkit-test` repo | Clean, purpose-built test environment; no risk of a platform bug hitting an existing project during testing |
| GitHub Marketplace publishing | Not pursued now; kept as a future option, and only for individual composite actions like `detect-changes` — reusable workflows (`ci.yml`, `security.yml`) can never be Marketplace-listed at all | The Marketplace lists at most one action per repo, and only from a root-level `action.yml` — incompatible with the current multi-action `actions/<name>/` layout without extracting the action into its own repo. Also requires a public repository. Publishing also flips the supply-chain trust direction: `checks-toolkit` would become the third-party that strangers' workflows trust with `contents`/`pull-requests` permissions, which calls for a higher stability/security bar (strict semver discipline, 2FA, careful secret handling) than while it's only self-consumed. Revisit only if `detect-changes` proves generically useful enough to be worth extracting |
| Actions repo layout | One repo (`checks-toolkit`) hosts every composite action (`actions/<name>/`), not one repo per action — same pattern as GitHub's own `github/codeql-action` (`init`/`analyze`/`upload-sarif` in one repo, one shared version tag) | No current driver for independent per-action versioning or Marketplace publishing (already deferred above). One repo keeps cross-action changes atomic (e.g. a `detect-changes` schema change and the `secret-scan` code that reads it land in one PR), keeps all architecture decisions in a single documentation source instead of fragmented across N repos, and composite actions can already be tested in isolation (proven with `detect-changes` via `act`) without needing a separate repo per action. Revisit only if one specific action should live and version independently (e.g. to publish it standalone) — splitting one action out later is far easier than merging many repos back together |
| Actions naming convention | Every capability-specific action follows a `<type>-<target>` pattern (e.g. `lint-python`, `audit-node`, `scan-secrets`) — the name always describes the concern being checked, never the specific tool implementing it | Keeps the promise from the "Actions repo layout" row real in practice: because the name never bakes in a tool, the tool inside an action can be swapped or extended later without a rename or a change to any caller (`ci.yml`/`security.yml`). Applied retroactively to what was first called `secret-scan` → renamed `scan-secrets` for consistency with `scan-docker`/`scan-terraform` |
| Security actions report, don't gate *(superseded by "Severity policy in the security actions", below)* | Security-relevant actions (starting with `audit-python`) never fail their own step just because they found something — they always report findings as structured outputs (a count plus the raw tool JSON) and exit successfully, unless the *tool itself* fails to run (a real execution error). Whether a finding should block the merge is decided later, centrally, by a not-yet-built severity-gate job that reads every security action's outputs | Matches the Mergify contract already in place: consumer repos see exactly two required checks (`CI gate`/`Security gate`), and the internal job structure can change freely. If every security action failed its own step on any finding, there'd be no single place left to apply a severity policy (CRITICAL/HIGH block, MEDIUM/LOW report-only) — the policy would end up duplicated, inconsistently, inside every action instead of living in one place |
| CodeQL/Semgrep bundling (`scan-code`) | CodeQL and Semgrep are not split into per-language actions (`scan-python`, `scan-node`); they're combined into one `scan-code` action that accepts which languages are present (`python`/`node` boolean inputs, derived from `detect-changes`'s `project.*`) and runs both tools once against the resulting language list | Per-language actions would duplicate fixed overhead (downloading/initializing the CodeQL CLI, installing Semgrep) once per language, on every PR that touches more than one language — wasted, since CodeQL's own `languages:` input already accepts a comma-separated list and builds/analyzes all of them within a single `init`/`analyze` call. GitHub's own matrix-per-language CodeQL template optimizes for wall-clock speed via parallel jobs, not for total compute — for a low-traffic solo/small-team repo, one sequential action avoiding duplicated setup is the more sensible trade-off. Semgrep has no comparable per-language build cost but is bundled the same way for consistency and to avoid a second tool install |
| Branch protection | Enabled on `development` once the repository is public, requiring `CI gate` and `Security gate` | Free for public repositories on any plan; private repositories need a paid plan. Until it is enabled nothing enforces the required checks, which is why the known limit of `check-workflows.yml` below stays open |
| Public history starts from one commit | The public repository starts from a single initial commit; the history of the earlier private repository is not carried over | Once public, every historical commit stays permanently browsable, so removing something in a later commit does not remove it. Starting clean after an audit is cheaper than cleaning history afterwards. The reasoning behind the early decisions is kept in this log instead |
| Third-party Actions policy | Only use GitHub Actions from official/verified publishers (GitHub itself, Docker, major cloud providers, etc.) or self-built ones — no actions from individual/random maintainers | A third-party action runs with the calling workflow's permissions and can see its secrets; a compromised maintainer account is a real, demonstrated supply-chain risk (e.g. the `tj-actions/changed-files` compromise in early 2025, where a popular changed-files action was hijacked to dump CI secrets into build logs). This is also why `detect-changes` is built in-house rather than adopting an existing changed-files action |
| `lint-markdown` tooling | One action, three independent steps: markdownlint-cli2 (blocking), codespell (blocking, `--builtin clear`) and lychee (report only unless `fail-on-broken-links`, which `ci.yml` ties to `fail-on-findings`). Platform default markdownlint config with line length and table style off; consumers override with their own config files. lychee runs from its official Docker image pinned by version **and** digest, in a container with a read-only mount, no capabilities and no secrets, with private/link-local addresses excluded | Structure and spelling are deterministic, so they block like `lint-python`. Link checks depend on third-party sites (rate limits, outages, bot blocking), so a failure often has nothing to do with the change; blocking by default would train people to ignore the check. Links in a PR are untrusted input, so the checker is isolated and cannot reach the runner's internal network or the cloud metadata endpoint. `lycheeverse/lychee-action` was not used: it is a community Action, outside the Actions policy, and the CLI needs no wrapper. Trade-offs: the npm and pip packages are pinned by version but not by hash, and transitive dependencies are unlocked; codespell is English-only, so Dutch files need a `.codespellrc` skip |
| `lint-terraform` in steps | Built step by step: `terraform fmt -check` first, `terraform validate` (needs `init -backend=false` and provider downloads) later. Terraform CLI installed with the official `hashicorp/setup-terraform@v4` at a pinned exact version, wrapper off. No credentials and no state anywhere in the platform's Terraform checks | `fmt` is purely syntactic: no `init`, no network, no providers, so it carries none of the supply-chain risk of `init` (providers and modules come from the PR itself). Starting there lets the riskier step be designed deliberately (lock file, no secrets, minimal permissions). Pinning the CLI version keeps an unchanged PR from changing result when HashiCorp releases. Exit code 3 from `fmt -check` means "would reformat"; any other non-zero code (e.g. a syntax error) is reported as a failure to run |
| No code-execution tests | The platform does not run the consumer's tests (`test-python`/`test-node` removed). Scope is static checks only: lint, typecheck, audit, scan, build | The platform exists to catch security issues and quality problems, not to verify that the application works — that is the consumer repo's own concern. Running a PR's tests also means executing untrusted code with the job's token and network access, which is a bigger trust boundary than reading it. `typecheck` stays: it analyses types without executing anything |
| Workflow checks | Two actions: `lint-workflows` (actionlint, correctness, blocks on any finding) and `scan-workflows` (zizmor, security, report-only until `fail-on-findings` is switched on). Run first by an independent `check-workflows.yml` on this repo; wiring into `ci.yml` for consumers comes later via a `detect-changes` signal | Different jobs and different inputs: actionlint reads workflows only, zizmor also reads composite `action.yml` and `dependabot.yml`, and both are useful on their own. zizmor starts report-only because its first run already finds 71 known issues (unpinned actions, template injection, credential persistence) that are open todo items. The checker is separate from `ci.yml` so a broken `ci.yml` can still be reported |
| Workflow checkers: supply chain | actionlint is installed from its GitHub release tarball with a **hardcoded SHA-256** (version and hash are inputs and must change together); zizmor from PyPI at a pinned version, run `--offline` with no token. No third-party Action wrapper | Neither project is an official/verified publisher under the Actions policy, so no Action wrapper is added. A hash-checked binary means a tampered release asset cannot run. zizmor offline needs no GitHub token and no network; the online-only audits are skipped. The zizmor wheel is pinned by version, not by hash (same as `codespell`) |
| zizmor first findings | Fixed: template injection in `detect-changes` (every `${{ }}` goes through `env:`; see also row "Untrusted values reach scripts only through `env:`", which adds ref validation), all actions pinned by commit SHA (version in a comment), Dependabot cooldown of 7 days. Accepted for now: `self-repository` is disabled in `.github/zizmor.yml`. Fixed afterwards: `artipacked` (every checkout now sets `persist-credentials: false`, see row "Actions pinned to commit SHAs; checkouts do not persist credentials") | Template injection was the only real vulnerability: `inputs.*` come from the caller. SHA pins plus a cooldown keep a moved or freshly compromised tag out while Dependabot still proposes bumps. `self-repository` asks for `$/...` instead of `./...`, but `ci.yml` calls platform actions from a separate checkout (`./.checks-toolkit/...`) for consumer repos; whether `$/` works there is unverified, so it is parked until tested |
| Known limit of `check-workflows.yml` | On `pull_request`, GitHub runs the workflow file from the PR. A PR can therefore change or remove the checker and skip its own check | Only branch protection / required checks from the base branch or required review prevent this, and branch protection is deferred (see row "Branch protection"). Accepted for now: single maintainer |
| Standalone-callable Actions | Every composite action (`detect-changes`, and later per-ecosystem checks) must work independently: explicit inputs/outputs, no hidden assumptions about only being called from `ci.yml`/`security.yml` | Reinforces the existing "Action = building block, Workflow = complete procedure" rule from architecture.md; keeps building blocks genuinely reusable outside this platform's own pipelines, not just internal cogs |
| Third-party all-in-one security SaaS (Aikido, Sonar, Snyk) | No added value for this platform — not adopted | Free tiers for public repos exist for all three, but they overlap almost entirely with tools already chosen: Aikido's SAST is a fork of Semgrep OSS and it also bundles secrets/container scanning (Gitleaks/CodeQL/Trivy territory); Sonar and Snyk cover the same SAST/SCA/container ground with different engines. Their real value-add (cross-tool triage/prioritization/dashboard) is exactly the orchestration layer this platform's own 3-layer security model and severity policy provide, so adopting one would duplicate the platform's own purpose. They also add a third-party SaaS trust/data-exposure boundary beyond the Actions-supply-chain concern already addressed |
| `detect-changes` signal matching (v1) | No weighting — a single weak signal (e.g. one `*.py` file) sets the capability to `true`, exactly like a strong signal (`pyproject.toml`) | Keeps the first milestone simple and matches the documented example in architecture.md; weighting/false-positive protection is deferred until it proves to be a real problem in practice |
| `detect-changes` base/head ref resolution | `base-ref`/`head-ref` are optional inputs, defaulting to values derived from `github.event_name`/`github.event` when not supplied | Keeps the action standalone-callable (per the Actions policy) while still working automatically when called from `ci.yml`/`security.yml` on `pull_request` or `push` |
| `detect-changes` diff mechanism | Compute `changed.*`/`components[]` via the GitHub API **compare endpoint** (`actions/github-script`), never local `git diff` — one uniform path for both `pull_request` and `push` events. `base-ref`/`head-ref` are always resolved first (bash `if`/`elif` on `github.event_name`: PR base/head SHA for `pull_request`, `before`/`after` for `push`), then `GET /repos/{owner}/{repo}/compare/{base}...{head}` is called with those two refs — the PR-files-by-number shortcut is not used | Keeps `detect-changes` independent of the caller's checkout depth/history entirely — no `fetch-depth` requirement, unlike a local `git diff` approach. One code path for both event types is simpler to reason about and test than branching between two different endpoints. Bonus: the compare endpoint only needs `contents: read` (already the workflow default) — no extra `pull-requests: read` permission required, unlike the PR-files endpoint. Trade-off: still needs pagination/truncation handling for very large diffs (the compare API also caps the `files` array around ~300 changed files, reporting `truncated: true`) |
| `detect-changes` output shape | Single JSON output (`result`) matching the documented `project`/`changed`/`components` schema, not flattened per-capability outputs | Matches the schema's own design goal — `components` is present from day one so future capabilities don't require an interface change; a flat output per capability would need a new output added for every new ecosystem |
| Dependency (SCA) scanning strategy | Per-capability **native** tool where one exists — Python → `pip-audit`, Node → `npm audit`/`pnpm audit`/`yarn audit` matching the detected lockfile, Docker → already covered by Trivy's image scan. A generic **OSV-Scanner** fallback covers any capability without a native tool (starting with Terraform). Dependabot alerts stay enabled separately as a maintenance layer (automatic update PRs), not the active CI severity-gate | Matches the existing Capability → CI mapping principle — each ecosystem already gets its own dedicated tools (Ruff/mypy/pytest for Python, etc.). Native tools are typically the most authoritative source for their ecosystem (`pip-audit` reads PyPI's own advisory data directly). OSV-Scanner (official Google/OSV.dev project) plugs the gaps without adding a bespoke tool per missing ecosystem. Dependabot's background alerts don't fit the active block-on-severity model this platform wants, but remain useful for staying current |
| Semgrep adoption | Add Semgrep as a second SAST layer alongside CodeQL, triggered on `changed.python` / `changed.node` / `changed.docker` (custom secure-coding rules + Dockerfile linting) | Fills gaps CodeQL doesn't cover: easy custom/org-specific rules and Dockerfile best-practice checks. Publishes its own official GitHub Action, so it fits the Actions policy. Overlap with CodeQL for shared languages is accepted deliberately (different detection approach — semantic dataflow vs. pattern matching), not treated as redundant |
| Terraform misconfiguration scanning | No separate Terraform-security tool — extend Trivy (`trivy config`) to scan Terraform files for misconfigurations, triggered on `changed.terraform` | tfsec's 1000+ checks were merged into Trivy (last independent tfsec release May 2025); reusing an already-adopted tool avoids unnecessary tool sprawl and keeps the footprint minimal, in line with the Actions/tooling policy |
| `scan-secrets` tool choice | **Gitleaks** for now; **Betterleaks** noted as the likely successor to revisit later, not adopted yet | Betterleaks (fork by the original Gitleaks author/team) adds real capability — Expr-based contextual filtering, live secret validation via async HTTP calls, BPE-based false-positive filtering — but is far less mature (~2k stars, v1.8.1, no known official Action yet) than Gitleaks (~21k stars, long track record, official `gitleaks-action`). Gitleaks is the safer choice to actually build `scan-secrets` on now; Betterleaks' validation feature fits the "report, don't gate" model well and is worth adopting once the platform's foundation is proven — revisit then, not before |
| `ci.yml` matrix failure model | Blocking vs. reporting is decided purely by **action type**, not per component: `lint`/`typecheck` genuinely fail their step/job on a real problem (plain GitHub Actions default behavior, no special handling); `audit`/`scan` never fail on their own findings (the existing "report, don't gate" pattern), only on a genuine tool execution error *(superseded: since the "Severity policy in the security actions" decision, `audit`/`scan` actions fail at `fail-on-severity` and above)*. No per-component override mechanism (no `continue-on-error`, no cross-matrix result aggregation via artifacts, no override input) | Keeps the matrix trivial: this split already matches what's built (`audit-python`) and what's about to be built (`lint-python`/`typecheck-python`), with zero extra machinery. A per-component exception (e.g. "let this one legacy path's lint fail without blocking") would need `continue-on-error` (which masks the true outcome from `needs.<job>.result`), an artifact-based aggregation step (matrix job `outputs:` don't aggregate across matrix instances by default — only the last completed instance's value survives), and a workflow input to override it — real complexity with no concrete need yet. Deferred; see "Known limitations" in [roadmap.md](./roadmap.md#known-limitations) |
| `ci.yml` matrix `fail-fast` | `fail-fast: false` on every per-capability matrix (`python`, `node`, `docker`, ...) | GitHub Actions' default (`fail-fast: true`) cancels the other still-running matrix instances the moment one fails. Monorepo components are independent of each other (a `backend` failure has nothing to do with `frontend`), so one component failing early shouldn't deny the others the chance to report their own result |
| Calling `ci.yml`'s actions from an external repo | Every job that calls a local action first checks `ops-lane/checks-toolkit` itself out into a `.checks-toolkit` subdirectory, then calls actions via the static local path `./.checks-toolkit/actions/<name>` instead of `./actions/<name>`. The `ref:` for that checkout comes from a **required `platform-ref` input** that every caller must set explicitly (`self-test.yml` → `${{ github.sha }}`; `checks-toolkit-test` → the literal tag it used in its own `uses:` line, e.g. `v0.1.0`) | A step's `uses:` can't contain a `${{ }}` expression at all (confirmed via a real parse error on a dynamic `uses:` in `test-action.yml`), so the target ref can't be interpolated directly into an `owner/repo/path@ref`-style reference — hence checking the repo out into a subdirectory and using a static local path instead. Plain `./actions/<name>` only worked because every test so far was `self-test.yml` calling `ci.yml` within `checks-toolkit` itself, where the checked-out repo happens to already contain `actions/`; an external caller (`checks-toolkit-test`) checks out its own code, which has no `actions/` folder at all. **First attempt failed**: resolving the ref from `github.workflow_ref` inside `ci.yml`'s own jobs seemed reasonable but is wrong — confirmed via a real failed run where it tried to fetch `refs/heads/main` (the *caller* `checks-toolkit-test`'s own branch) from `checks-toolkit` instead of the intended tag. Every `github.*` context value read inside a called reusable workflow reflects the top-level triggering context, not the specific reusable workflow being invoked — there is no context field that tells a reusable workflow which ref of itself is currently running. The caller is the only party that actually knows this (it wrote the `uses:` line), so it must pass it explicitly; a required input surfaces a clear validation error if a future caller forgets it, rather than a confusing runtime failure |
| Audit findings reaching the gate | No central aggregation job or artifact-based collection. `audit-python` gets a `fail-on-findings` input (default `false`) and decides for itself whether to fail; it also writes its findings to `$GITHUB_STEP_SUMMARY`. `ci-gate` needed zero changes | Considered building a matrix-wide artifact-collection step feeding a dedicated policy job, but two things made it unnecessary: (1) `pip-audit` has no severity field, so there's no graded policy to evaluate centrally anyway — only an all-or-nothing "did anything get found" question, which the action itself can already answer; (2) GitHub Actions already rolls up a matrixed job's own conclusion to `failure` if any instance fails (with `fail-fast: false` still letting sibling components finish), so `ci-gate`'s existing `needs.<job>.result` check already detects a failing `audit-python` instance with no new plumbing. `$GITHUB_STEP_SUMMARY` is per job-run, so each matrix instance's findings already surface as their own labeled section on the run's Summary page — no cross-job aggregation needed for visibility either. Revisit only if a severity-aware, cross-component policy is ever needed (would require a real severity data source first, e.g. OSV-Scanner) |
| Capability jobs stay bundled; splitting out `audit` is the known next step | Each capability job keeps all of its actions (lint → typecheck → audit) as steps of one matrixed job, instead of one job per action | Compared with a quality-gates setup that gives every check its own job and lets the gate pick which failures block via a configurable set. That model is more flexible, but with a job per action every job repeats the two checkouts (the platform checkout can't live inside a composite action, since the actions only exist after it) — a lot of YAML for a solo platform. The ceiling of the bundled model: the gate sees one result per capability job, so an audit finding can't be both visible *and* non-blocking — the audit step is either green (and the table says "passed" despite findings) or it fails the whole job. Revisit by splitting only `audit` into its own job, with the gate holding a configurable blocking set, once findings need to show as "failed, non-blocking" in the result table |
| `ci-gate` reports per component and step; verdict is independent of the report | The gate evaluates `needs.*.result` first (fail closed), then builds a result table from the Actions jobs API (one row per `<type>-<target>` step of every matrix instance) into `$GITHUB_STEP_SUMMARY` and, on `pull_request` events, into one sticky PR comment (found by an HTML marker). Reporting steps are `continue-on-error`; the verdict is enforced in the last step and never depends on them | The matrix-output-aggregation problem (no artifacts needed) disappears because the jobs API already lists every matrix instance as its own job with per-step conclusions. Consumer contract consequence: the gate job requests `actions: read` (jobs API) and `pull-requests: write` (comment), and a called workflow can't be granted more than its caller allows — a caller that doesn't grant them gets the whole run stopped at startup, not just a failed comment step. Callers must therefore declare these permissions (documented in `workflows.md`). On fork PRs the token is read-only, so the comment is skipped and the table remains in the job summary |
| Gate logic lives in `actions/ci-gate`, not inline in `ci.yml` | The `CI gate` job is a platform checkout plus one call to the `ci-gate` composite action (verdict, result table, PR comment). The capability jobs stay in `ci.yml` | The gate was ~130 lines of bash/jq inside the workflow and is the one piece that is a self-contained building block (explicit inputs: the `needs` JSON and a token; one output: `failed`), in line with "actions are building blocks, workflows are procedure". `needs` has to be passed in as `toJSON(needs)` because a composite action can't read that context itself. Cost: the gate job now needs the platform checkout too, which it didn't before. The repeated checkout pair in the other jobs can't be moved into an action (the actions only exist after that checkout), and per-capability composite actions were rejected: the jobs API lists a composite action as a single step, which would erase the per-step rows in the result table |
| `checks-toolkit-test` follows `development`, not a tag, while the platform is being built | The test repo's `ci.yml` calls `ci.yml@development` with `platform-ref: development` instead of a pinned tag | Every platform change otherwise needs a tag plus a bump in the test repo before it can be tried (found with the first external runs: a one-line fix would have cost a new tag). A moving ref is acceptable here because the test repo exists only to exercise the platform; real consumers still pin to a tag, as in the `Versioning` row. Switch the test repo back to the newest tag once the platform is stable enough to tag regularly |
| `audit-terraform` / OSV-Scanner for Terraform dropped | `audit-terraform` is removed. OSV-Scanner cannot scan Terraform: the scanning engine under it (`osv-scalibr`) has no Terraform extractor and `Terraform` is not an ecosystem in the OSV vulnerability schema (checked against both repositories, October 2026). Terraform stays covered by `scan-terraform` (misconfigurations) and `lint-terraform` | Closes the open research item from the todo list. Providers are not packages in any vulnerability database OSV aggregates, so there is nothing for a Terraform "dependency audit" to match against. Keeping a placeholder action that can never work would only mislead |
| What lives in `ci.yml` versus `security.yml` | `ci.yml` = quality: `lint-*`, `typecheck-*`, `build-docker`. `security.yml` = everything that looks for vulnerabilities: `scan-secrets`, `scan-code`, `scan-docker`, `scan-terraform`, `audit-python`, `audit-node`. `audit-python`, `scan-docker` and `scan-terraform` moved out of `ci.yml` into it. Each workflow ends in its own gate job (`CI gate`, `Security gate`) | Matches the contract that consumers get exactly two required checks (`CI` and `Security`) and that a vulnerability shows up as a Security failure, not a CI one. The cost is that the Docker image is built twice (once in `ci.yml` to prove it builds, once in `security.yml` to scan it), because separate workflows cannot share a local image. Accepted: building twice is cheaper than coupling the two workflows |
| Severity policy in the security actions | Every tool that reports a severity (`audit-node`, `scan-docker`, `scan-terraform`, `scan-code`) has a `fail-on-severity` input, default `high`: critical and high fail the step, lower findings are only reported in the job summary. The threshold is applied inside each action; `security.yml` exposes one `fail-on-severity` input that is passed to all of them. Tools without severity are all-or-nothing: `scan-secrets` always blocks (`fail-on-findings`, default true) and `audit-python` (pip-audit has no severity field) reports unless `fail-on-findings` is set | Implements the CRITICAL/HIGH-block, MEDIUM/LOW-report policy from the todo list and replaces the earlier plan of a central severity-gate job. A central job would have needed every action's findings passed through artifacts; with the threshold inside each action the gate stays what it was (a verdict from `needs.*.result`) and a tool can still be used standalone. Severity names differ per tool (npm says moderate, Trivy says medium; `audit-node` accepts both); CodeQL's `security-severity` score maps to 9+ critical, 7+ high, 4+ medium, below that low; Semgrep has no critical, so ERROR counts as high, WARNING as medium, INFO as low. Trivy runs with `--ignore-unfixed` by default: a finding nobody can fix by updating should not block a pull request |
| Security tools run as pinned container images, not third-party Actions | Gitleaks, Trivy and Semgrep run as `docker run` of their official images, pinned by version and digest (same pattern as lychee in `lint-markdown`): read-only mount of the code, `--cap-drop ALL`, `no-new-privileges`, the runner's own user, no tokens or secrets. Trivy gets the image as a tar file instead of the Docker socket. CodeQL is the exception: it only exists as GitHub's own `github/codeql-action`, pinned to a commit. `scan-terraform` was first built on `aquasecurity/trivy-action` (pinned by commit SHA, with the Trivy version as an input); it was changed to the container so that it and `scan-docker` share one pinned Trivy and the same lockdown, and so the severity threshold (`fail-on-severity`) works the same in both | The code being scanned is untrusted input to a parser, so the tool runs in a box with nothing to steal. A digest cannot be re-pointed, which also removes a wrapper Action (and its maintainers) from the supply chain. For Gitleaks it is also a practical need: the `gitleaks-action` requires a paid license key for organization-owned repositories, the plain tool does not. The earlier "verify exact repo name" notes for these three Actions are therefore obsolete |
| Gitleaks ignores the scanned repository's own config | `scan-secrets` always passes the platform's `gitleaks.toml` (built-in rules only) and points Gitleaks at a non-existent ignore file. A `.gitleaks.toml` or `.gitleaksignore` committed in the scanned repository is not used. Verified by test: a pull request that adds an allowlist for its own secret is still caught. It scans the commits of the pull request (`base..head`, so a secret added and removed again within it is found), and falls back to the full history when no valid range exists (new branch, base not a commit, base equal to head) | Gitleaks reads its config and ignore file from the scanned code by default. For a pull request that means the author can hide a secret by editing those files in the same pull request. The price is that a repository cannot silence its own false positives; a per-repo allowlist would have to be read from the base branch, not the pull request, and is a later step |
| `skip-ci` is implemented in the `detect` job and the gate | The `detect` job of both workflows checks the pull request labels and outputs `skip`. Every other job has `skip != 'true'` in its `if:` and is skipped; the gate job always runs, reports "skipped via skip-ci" instead of a result table, and passes. This replaces the earlier idea of every job running as a no-op step. Consumers must include `labeled` and `unlabeled` in their `pull_request` trigger types, otherwise adding the label does not start a new run | A required check is the gate, which always runs and always finishes, so the "required check stays pending forever" problem the no-op idea was meant to solve cannot occur, and no job needs extra skip logic. Only the `pull_request` event can skip; a push or manual run never does. Who may set the label is still a repository setting (Mergify later), not something the workflow can enforce |
| Dockerfile linting lives in `scan-code` (Semgrep) | Semgrep's Dockerfile rules (`p/dockerfile`) run inside `scan-code`, enabled by its `docker` input. There is no separate `lint-docker` action and `scan-docker` stays a pure image scan | Closes the open placement question. `scan-code` already runs Semgrep once over the repository; one more rule set costs almost nothing, whereas a `lint-docker` action would be a third place that installs and runs Semgrep. Dockerfile findings (for example "no USER, runs as root") are security findings, so they belong in `security.yml` |
| Node actions install dependencies without lifecycle scripts; yarn is unsupported | `lint-node` and `typecheck-node` use the project's own ESLint and TypeScript, which needs its dependencies, installed with `npm ci --ignore-scripts` or `pnpm install --frozen-lockfile --ignore-scripts` (pnpm pinned, run through `npx`, no global install). If the project has no ESLint, or no `tsconfig.json`/TypeScript, the step is skipped with a visible warning. `audit-node` reads the lockfile only and installs nothing. yarn is not supported yet: the actions warn and skip rather than guess | Lifecycle scripts (`postinstall` and friends) are arbitrary code from the pull request, and linting does not need them. The project's own lint config is still code that ESLint executes, which is why these jobs run on ephemeral hosted runners with a read-only token; that matters again if self-hosted runners are introduced. A skipped check is shown as skipped in the job summary, never as a silent pass. yarn adds a second, version-dependent command set (classic versus berry); better a clear gap than a half-working guess |
| `mypy` runs without the project's dependencies | `typecheck-python` installs only mypy (pinned) and runs it with `--ignore-missing-imports` by default (an input turns that off). The project's own dependencies are not installed | Installing them means running the pull request's own `setup.py`/build backend. Without them mypy cannot resolve third-party imports, so it would report every one as an error. The trade-off is weaker checking of code that calls third-party APIs, in exchange for never executing the pull request's build code. Python's own code and the project's mypy config are fully checked |
| `detect-changes` outputs the refs it resolved | New outputs `base-ref` and `head-ref` on `detect-changes`, so `scan-secrets` scans the same commit range that change detection compared | One source of truth for "which commits does this run cover". Purely additive: the `result` schema is unchanged, so this is not a breaking change to the contract |
| Untrusted values reach scripts only through `env:` | No `${{ }}` expression is written into a `run:` script or a `github-script` `script:` any more; the values are passed as `env:` variables (and read as `process.env` in JavaScript). This was done everywhere it occurred, all in `detect-changes`. `detect-changes` also requires `base-ref`/`head-ref` to be 40-character commit SHAs and fails otherwise. The rule is written down in [contributing.md](./contributing.md#security-rules-for-workflows-and-actions) | The `Write summary` step used to contain `RESULT='${{ ...result }}'`. `result` includes component paths, and those come from **file names in the pull request**. A directory named `x'; <command>; echo '` closed the quote and ran `<command>` on the runner; this was reproduced locally before the fix (a file got created) and is no longer possible after it (the same name is printed as text). The job holds the repository token and, for same-repo pull requests, `platform-read-token`. An environment variable is only ever data, which makes the fix a pattern rather than an escaping exercise. The SHA check is defense in depth: refs end up in an API URL and in `$GITHUB_OUTPUT`, and a branch name was never a documented value |
| Actions pinned to commit SHAs; checkouts do not persist credentials | Every `uses:` in `.github/workflows/` and `actions/` is pinned to a full commit SHA with the version as a comment (`actions/checkout`, `actions/github-script`, `hashicorp/setup-terraform`; `github/codeql-action` already was). Every `actions/checkout` sets `persist-credentials: false` | A tag can be moved by whoever controls the action's repository, so `@v7` is a promise rather than a fact; the earlier "Third-party Actions policy" already cites a real tag-hijack incident, and pinning is what makes that policy enforceable for official actions too. By default `checkout` leaves the token in `.git/config`, where any later step can read it, including steps that run the pull request's own code (ESLint config, Docker build). No step needs git credentials after the checkout (the platform checkout is only read, change detection uses the API) |
| `pull_request_target` is refused | The `detect` job of `ci.yml` and `security.yml` fails with an explanation when `github.event_name` is `pull_request_target` | `pull_request_target` gives a fork's pull request a read/write token and secrets; these workflows check out and run code from the event, so allowing that trigger would run untrusted code with full access, or at best silently scan the base branch instead of the pull request. The platform cannot stop a consumer from choosing that trigger, but it can make the mistake loud. Everything downstream depends on `detect`, so the gate fails too |
| Dependabot covers the composite actions; 7-day cooldown | `dependabot.yml` lists `/` and `/actions/*` (it only finds an `action.yml` in a listed folder, so the actions' own pins would otherwise never be updated) and sets `cooldown: default-days: 7` | Without the extra directories the pins in `actions/*/action.yml` would silently go stale. A cooldown means a release is only proposed a week after publication; compromised releases of popular actions have typically been caught and withdrawn within days. Container digests, pip versions and the pnpm version cannot be updated by Dependabot and are bumped by hand — listed in [contributing.md](./contributing.md#pinned-versions) |
| Python tools pinned to exact versions | Ruff, mypy, pip-audit, Poetry (+ the export plugin) and pipenv are installed with `==<version>` (codespell and markdownlint-cli2 already were) | A verdict must not change because a tool released a new version while the pull request stayed the same. The cost is maintenance (a table of pins to review), which is accepted for the tools that decide pass or fail; Dependabot cannot help here |
| `SECURITY.md` and a single `CODEOWNERS` entry | `SECURITY.md` points to GitHub's private vulnerability reporting, states best-effort handling by one maintainer, lists what is in and out of scope, and promises neither response times nor a bounty. `.github/CODEOWNERS` assigns everything to the maintainer | These files run in other people's pipelines, so reports must have a private channel. Promises that a solo maintainer cannot keep would be worse than none. `CODEOWNERS` only becomes binding with the branch protection rule "Require review from Code Owners"; with one maintainer that rule would block the maintainer's own merges, so it is not switched on by default |
| Repository language is English | Documentation, comments, commit messages, issues and pull requests are in English; `codespell` assumes English | A public repository needs one language its readers share, and the spell check only works for one. The project started with Dutch planning notes; those were private working notes and are not part of the published documentation |
| `detect-changes` lists files through the Trees API for a new branch | When the base is git's empty tree (a first push on a new branch, where there is nothing to compare against), the changed files are every file in the head commit's tree (`git.getTree`, recursive) instead of the compare API. All other cases still use the compare API | The compare endpoint only accepts commits and answers 404 for the empty tree, so the "every file counts as changed" fallback in "Resolve base and head refs" could never work; found by running the self-test with that base on a real runner (it had never been exercised). The Trees API accepts a commit SHA and needs only `contents: read`, like the compare call, so the "one uniform, checkout-independent mechanism" reasoning of the diff-mechanism row still holds |
| CodeQL is behind a switch, off by default | `scan-code` and `security.yml` have a `codeql` input, default `false`. When off, only Semgrep runs and the job summary says CodeQL is off, with a notice in the log. Whoever owns the repository turns it on once the repository is public or has GitHub Advanced Security | CodeQL cannot run on a private repository without Advanced Security, and the failure would make the whole Security gate red for every private consumer with Python or Node, however clean the code. An explicit, deliberate switch was chosen over auto-detecting the repository's visibility: a security check that quietly turns itself off is the behavior this platform tries not to have, and some private repositories do have Advanced Security. The cost is that nobody gets CodeQL until they ask for it, which the README and the roadmap say plainly |
| The runner image is pinned to `ubuntu-26.04` | Every job in `ci.yml`, `security.yml`, `check-workflows.yml` and `test-action.yml` has `runs-on: ubuntu-26.04` instead of `ubuntu-latest`. `.github/actionlint.yaml` tells actionlint the label is valid, because its newest release (1.7.12, March 2026) predates Ubuntu 26.04 and reports it as unknown. The pin is bumped on purpose, after a run of the test consumer | GitHub moves `ubuntu-latest` to Ubuntu 26.04 from 2026-10-19 over several weeks, and the preinstalled tools, versions and system libraries change with it, so an unchanged pull request could start to behave differently. That is the same reason every tool in this repository is pinned. 26.04 was chosen over 24.04 because that is where the label is heading anyway, and moving once, on purpose and tested, beats moving by surprise. The cost is a manual bump when the next release comes, listed in [contributing.md](./contributing.md#pinned-versions). Consumers are not affected: a reusable workflow's jobs run on the image the workflow names, whatever the caller uses |
| Exact tags, no moving major tag | Releases are exact tags (`v0.1.0`, `v1.2.3`); there is no `v1` that is moved forward. Every release also gets a GitHub Release (pre-release flag for `v0.x` and release candidates), and a published release is immutable. This replaces the earlier plan in `contributing.md` to move the major tag after every release | The whole project is about not trusting anything that can change under you (pinned SHAs, pinned digests, exact versions). A moving major tag would hand every consumer whatever the latest commit of a major is, and a compromise of this repository would reach all of them at once. A platform that demands pinning from others should be pinnable itself. Updating becomes a consumer decision, helped by Dependabot, which reads GitHub Releases and shows the notes. The cost is slower propagation of fixes; a moving major tag can be added later, the reverse cannot be taken back |
| Release pipeline: manual, typed version, notes only in the GitHub Release | `release.yml` is started by hand with the version typed in and a dry-run switch that defaults to on. It validates, builds the notes with git-cliff and creates the tag and the Release in one call, as the only job in the repository with `contents: write`. The Releases page is the changelog; `CHANGELOG.md` only points to it. `git-cliff` runs as the official image pinned by digest, as an unprivileged user with the repository mounted read-only. Its suggested next version (`--bumped-version`) is shown but never used | A person chooses the version because the commit types only say what changed, not how risky it is, and for `0.x` the bump rules are not standard. A dry run that is the default makes the first real attempt safe. Not writing a changelog file keeps the pipeline from needing to push to a protected branch or open pull requests (the setting that allows the latter is one the hardening list switches off). Creating the tag on the validated commit via the release API avoids a separate push and cannot tag a different commit than the one checked. Refusing a commit with failed or running checks and a version that is not higher than the last stable one prevents the two likeliest mistakes |
| Hand-written notes override generated ones | `.github/release-notes/v<version>.md`, if present, is used as the release notes instead of git-cliff's output. Used for `v0.1.0` | The history is squashed before going public, so the first release has no commits to build notes from. A hand-written file is also the escape hatch when a commit subject turned out wrong. It is a file in the repository, so it goes through review like any change |
| Conventional Commits are enforced on pull requests | The `check-commits` workflow runs `actions/lint-commits` on every pull request to `development` and fails when a non-merge commit has no `type(scope): description` subject | git-cliff only puts conventional commits in the notes (`filter_unconventional`); without enforcement a badly named commit would silently disappear from the release notes. A check is the only way to make sure that does not happen unnoticed. The cost is friction for contributors, accepted because the format is small and the failure message lists the offending commits. Commit messages are untrusted text and are only ever read into variables and printed indented |
